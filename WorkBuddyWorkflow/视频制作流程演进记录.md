## 一、当前流程是什么（一句话版）

```
概念帧(SVG→PNG) → ComfyUI/Wan2.2 I2V 生成底板素材 → ffmpeg 建 base 分段
   → Puppeteer 逐帧渲染透明覆盖层(data-t + FNS 动画) → 覆盖层 × base × BGM 合成成片
```

核心优势：**完全确定性**（`render(lt)` 按全局时间逐帧算，无 CSS transition/随机数），
所以任何一帧都能复现、能定位、能对比。这是它对的方向，不要动。

## 二、实测痛点（这次做片真实卡住的点）

| # | 痛点 | 具体表现 | 代价 |
|---|------|---------|------|
| 1 | **改一个字要全片重渲染** | 覆盖层 3281 帧逐帧截图 + ffmpeg，一轮 ~30–40 分钟 | 每调一句文案/一个字号就是半小时起 |
| 2 | **ComfyUI 生成脆弱** | 双专家第二段 `KSampler(node 10)` 峰值 ~9–10GB；被外部进程瞬时抢占显存就 OOM | 白等 9–15 分钟还失败；本次 s14 连挂两次 |
| 3 | **GPU 门控只看利用率** | `gpu_gate` 原来只查 util%，漏判"利用率 3% 但显存被占 9GB" | 带着 OOM 风险提交 |
| 4 | **机理动画各写各的** | HPA 轴(s5)、奖赏回路(s6)、生物钟曲线(s4/s13) 都是手写 SVG+JS | 新加一个机理分镜要 ~100 行 |
| 5 | **QC 靠整片** | 想看某分镜文字排版/时序对不对，只能等整片出来 | 反馈回路太长 |

## 三、已经落地的优化（本次已改进代码）

1. **`gpu_gate.py` 加"空闲显存下限"硬门槛**（`GPU_FREE_FLOOR_MIB = 9000`）
   - 提交前除利用率外，还要求空闲显存 ≥ 9GB；不足就让渡等待。
   - **这道门槛能直接挡住本次 s14 的 OOM**——它挂就是因为外部进程瞬时占了 ~9GB，而旧门控看利用率只有 3% 就放行了。

2. **`scene_preview.js` 单镜秒级预览**（新工具）
   - 只渲染目标分镜的覆盖层，`--base` 时叠到底板对应帧，采样几帧出图。
   - 调文案/字号/时序时 **~15 秒** 出结果，替代 30 分钟全片重渲染。这是反馈速度提升最大的一个。
   - 例：`node scripts/scene_preview.js s6 5 --base`

3. **s3 放慢与文案重排**：`FNS.s3` 用 `lt/=1.25` 把本地时间压回"设计时刻表"，
    Morph/读数/文案随更慢的眼视频一起延展，**水滴落点仍精确等于眼皮合上那一拍**——
    "视频慢一点"和"声画同步"不再二选一。

## 四、可评估的 skill / 插件 / 内置工具

| 能力 | 现状 | 建议 |
|------|------|------|
| **内置 `VideoGen`**（文/图→短视频 mp4） | 可用（deferred 工具） | 给**非关键空镜/B-roll/预演**做快速备选：无需 GPU 门控、无 9 分钟等待。缺点：时长偏短、对"逐帧确定性合成"管线控制力弱。建议对 1–2 个氛围镜做 A/B 对比再决定是否引入 |
| **内置 `ImageGen`**（文→图） | 可用（deferred 工具） | 用来生成**更精致的 I2V 概念首帧**（现在用 `concept_render.js` 画 SVG 首帧；ImageGen 可能给出更有质感的第一帧，喂给 Wan2.2） |
| **技能市场（视频类 skill）** | 本环境市场不可用（404） | 暂无专门"视频生成"技能可装；不虚构。真正的提速在工作流层（见三） |
| **连接器（视频/素材类）** | 无匹配项 | 本地 ComfyUI + ffmpeg + Puppeteer 已是合适栈，不建议为此接外部服务 |
| **办公类 skill**（pptx/docx/sheet） | 可用 | 与视频无关；仅当要把分镜表/台词导出成文档时用 |

> 结论：**没有"装个 skill 就提速"的银弹**。这套流程的提速点在工程层——①单镜预览（已做）②显存门槛（已做）③机理动画模板化（建议做）。

## 五、建议的后续采用顺序（按性价比）

1. **马上用**：`scene_preview.js` —— 之后每次改文案都先跑它，确认再全片合成。
2. **已生效**：`gpu_gate` 显存门槛 —— 之后批量生成不再轻易 OOM。
3. **值得做**：把"节点依次点亮 + 光点沿边传递 + 标签淡入"抽成一个 `mechanism()` 助手，
   HPA 轴/奖赏回路/生物钟都复用它，新机理分镜从 ~100 行降到 ~10 行。
4. **评估中**：用内置 `ImageGen`/`VideoGen` 对 1–2 个空镜做备选，比对观感与耗时后再决定。

## 七、第二轮：拿流程回头改已完成的片子（2026-10）

片子早就做完了，这轮是**按 SOP 回头改**——先跑闸门找缺陷，再改，再复检。结果发现了流程本身的几个盲区，比片子的问题更有价值。

### 7.1 最严重的问题：预览工具一直在骗人

`scene_preview.js` 里有这么一行：

```js
await page.evaluate(()=>{document.body.style.background='#0b0f14';});
```

本意是让覆盖层截图有个深色底、方便查看。但 `omitBackground` 只忽略**默认**背景，body 显式设的底色照样会被画进去——于是覆盖层截图变成不透明，叠到底板时把 base **整帧盖掉**。

后果：`--base` 预览里从来没有底板。连续几轮预览都显示"排版完美"，直到合成才发现 s8 的文字压在三个浅色液体柱上、几乎不可读。

**教训（已写进通用流程第 7 节）**：
- 预览工具必须用"已知应该出现的底板特征"自检，看不见就是链路断了
- **失真的预览比没有预览更危险**，它给的是虚假的通过信号

### 7.2 流程缺了一道判据：文字可读性

三道闸门（JS 报错 / 节奏 / 音画）全都测不到"文字压在亮背景上"。而这类问题恰恰是观众最先感知的。

这轮发现三处：s8 压液体柱、s9 压亮粉窗帘、s7/s11 压人脸。三处的解法各不相同（底衬 / 描边 / 全局描边加强），但根因是同一个：**文字和素材层分开开发，没人检查它们的叠合结果**。

已在闸门①加入对比度检查，并在"做覆盖层"步骤前置要求"先看底板亮度再定文字位置"。

### 7.3 判据的边界，这次量清楚了

s6 加了尾迹、节点脉冲、粒子流三样东西，静止占比只从 73.7% 降到 61.8%；s13 加了流动光点，38.4% 一动不动。

原因：判据算的是**全画面帧间平均绝对差**（240×428 下采样），一个 r=8 的光点对它的贡献不到 0.0005，阈值是 0.0012。

**结论**：
- 小元素改善观感，但推不动判据
- 要推动判据必须大面积或高对比变化
- **判据通过 ≠ 观感好**，s9 的可读性修复只让判据动了 1 个百分点，但那是观众真正能感知的改进

已写进通用流程第 7 节「判据在测什么」。

### 7.4 结构性问题的边界也清楚了

s5（18.2s）和 s6（17.1s）合计占全片 26%。这两镜的素材本身就是静态的（星空、剪影），覆盖层怎么加动效都只是"看起来在动"。

**根因是镜头太长，不是动效不够。** 覆盖层能救的范围到这里为止——再往前就必须重建 base 分段（重新跑 AI 生成素材）。这条边界写进了第 1 步判据："无 >12s 长镜"。

### 7.5 新增的两条工程规则

都是差点踩、或者踩了才发现难查的：

| 规则 | 场景 |
|---|---|
| 单镜样式必须 `#sN` 限定 | 想给 s8 文字块下移，差点直接改 `.txt{bottom}`，那会移动全片 13 个镜头的文字 |
| absolute 块必须算垂直占位 | s8 的额度条在 828px、文字块顶部约 860px，只差 32px；重叠在缩略图上看不出来 |

### 7.6 这轮改动对判据的实际影响

| 镜 | 静止占比 | 说明 |
|---|---|---|
| s8 | 50.5% → 42.7% | 唯一从"静止偏多"转为通过的镜头 |
| s6 | 73.7% → 61.8% | 加了大量动效，仍未过 45% 线 |
| s5 | 57.1% → 51.1% | 最长静止 2.29s → 0.83s（循环放电有效） |
| s13 | 38.4% → 38.4% | 观感改善，判据无变化 |

全片：音画差 0.011s，音频 mean -15.6dB，最长静止全镜 ≤3s。

### 7.7 留给下一轮

- s5/s6 缩短 3–4 秒（需重建 base 分段，要跑 GPU 生成）——这是唯一能真正解决静止占比的办法
- 把"预览工具自检"做成脚本：合成前自动比对"预览图与成片同帧的像素差异"，超过阈值就报警

## 8. 第二支片《为什么晕车时闭眼不管用》：从「画面质量」转向「工期」

前七节都在讨论**画面怎么更好**。这一节不一样——成片质量是合格的（三道闸门全过），
问题是**过程太慢**：136 秒的片，墙钟 59 小时。

完整复盘见 [`第二支片复盘.md`](第二支片复盘.md)。这里只记**决策层的三条改动**和理由。

### 8.1 时间账：只有 16% 在做真正的生成

| 项 | 时长 | 占比 |
|---|---|---|
| GPU 实际执行 | 9.7 h | 16% |
| 门控让渡（等别人用完卡） | ≥10.1 h | 17% |
| s8 卡死堵住整条队列 | 15.6 h | 26% |
| 覆盖层/底板/合成/质检/文档 | ~8 h | 14% |
| 夜间空转、会话中断 | 余下 | 27% |

**结论**：慢的不是单镜速度，是**架构把最贵的资源放在了关键路径上**。

### 8.2 决策一：分镜阶段就要定「素材来源」

上一支片的做法是 18 镜全部 I2V。这一支片照抄了，结果 7 镜本该代码渲染，白花 3.9 小时，
而且结构还画错了（三个半规管画成交叉线框，观众数不出"三个"）。

→ **分镜表加三列**：素材来源 / 物理约束 / 预算。
→ 判据：「观众要数清结构吗？」→ 代码；「要相信是真的吗？」→ AI。（详见通用流程 §3.0）

**为什么这条最重要**：它不改任何单镜的质量，但它决定整支片要不要排 GPU 队列。
一个字段填错，代价是几小时。

### 8.3 决策二：假设先跑小样，再写进文档

这一轮犯了个典型错误：看到 WanGP 配置注释写"8 步三相位可减少慢动作效应"，
直接写进 SOP 当建议，还花 16 分钟跑了实验版——结果是扫描线撕裂 + 色边的废片
（`cfg=3.5` 对已蒸馏的 FP8 权重过猛）。

→ **规则**：任何"换采样器/换模型/换参数"的判断，写进文档前必须有单镜小样。
→ 理由：**没验证的建议比没有建议更危险**，它会被下一支片当既定经验执行。

### 8.4 决策三：验收必须加「人眼抽帧」

三道自动闸门全过，但成片里 s14/s17 有换行孤字、s6 结构画错——**自动判据一个都没抓到**。

→ **规则**：成片至少抽 2 轮 × 8~9 帧，覆盖全部镜头，逐帧看可读性与结构。

### 8.5 没有改的：分层架构

三层分离（素材/覆盖层/音轨）这一轮救了返工成本：
s14/s17 的断字问题只花了 7 分钟重合成，没动素材。
**架构没问题，问题在排产。** 这也是为什么改动集中在「决策前移」而不是「渲染优化」。
